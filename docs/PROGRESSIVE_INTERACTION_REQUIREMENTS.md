# 渐进式协作与统一对话交互整改需求

日期：2026-10-30。状态：需求基线；实施结果见 [实施验收记录](PROGRESSIVE_INTERACTION_ACCEPTANCE.md)。界面继续使用英文。

## 1. 本次纠正的设计原则

用户应按自己已经了解的信息逐步决定。系统不能把后台自动编排顺序等同于用户认可的业务顺序。

- 先解决当前明确目标，再征得对具体方案的认可，最后进入有关联的下一阶段。
- 训练方向认可不等于训练立即生效；饮食检查不等于允许修改饮食；老板批准不等于会员接受；读过提醒不等于业务已处理。
- 保留一个对话时间线和输入框，以及原来的普通业务子页面。
- 查询不切换角色；明确进入某个专业领域的修改或深入咨询时，切换至负责该目标的角色并持续由其接待。
- 只显示当前阶段需要的决策，不提前列出后续所有可能选项。

## 2. 已核实的现状和原因

| 当前实现 | 后果 | 修改要求 |
|---|---|---|
| ConversationView 先渲染 messages，再渲染 requests | 旧任务和新任务状态集中堆在消息下方，用户需向上找具体草稿 | 用有稳定顺序的统一事件时间线展示消息、阶段结果、决策和回执 |
| 任务卡片与消息内的操作重复存在 | 同一任务出现多个 Review 入口，状态和目标不一致 | 每个阶段保留一个主要决策卡，其他入口引用相同对象与当前状态 |
| intent_router 的规划委派不会改变当前接待角色 | 用户问训练，顶部和接待回复仍是 Nutrition | 明确训练修改进入 Coach；查询不强制换人 |
| coach_runtime 生成成功即排入 Nutrition 工作 | 训练尚未商量好，饮食检查已经完成 | 增加会员认可训练方向的持久化阶段，未认可不派发 Nutrition |
| 部分 TrainingCandidate / Review plans 只打开 plans 总页 | 先看到现有食谱，无法直达训练草稿 | 所有入口传递具体 plan/request/pair ID 和阶段，打开目标详情 |
| cycle_requests 根据服务权限自动决定 coordinate_nutrition | 有营养服务权限被误当成会员授权进入饮食阶段 | 权限只决定能力可用；进入下一阶段还需符合当前流程与会员决定 |

上述现状来自本次源码检查；下述跨模块流程表是整改目标，不表示每个模块都有相同的已复现缺陷。

## 3. 训练修改的完整目标流程

### A. 识别目标，Coach 接待

用户明确说“把训练改简单一些，每次不超过30分钟”：切换到 Coach，简短提示 `Coach is helping with your training update.`，继承原始请求和资料，不要求重说。
如果用户只在查询训练安排，当前角色读计划回答，不生成新草稿、不切换。
若修改目标不清晰，Coach 只问必要问题；不能把“更简单”自行改成减重或增加训练天数。

### B. 训练草稿与多轮讨论

Coach 返回训练草稿的摘要、变化、原因和时长，只有训练内容：
- `View training draft`：打开这一版训练草稿详情。
- `Continue with this training`：认可这一版训练方向，进入下一阶段，尚未启用。
- 用户直接输入“再少一个动作”等意见：修改当前草稿，不新建冲突的独立任务，不要求去 Activity 取消后重新来。
- `Cancel update`：退出本次修改，保留当前有效计划。

草稿应可在对话中预览核心内容，不强迫先去子页面才能知道改变了什么。尚未认可时，不派发 Nutrition，不收费调用它做后续检查。

### C. 会员认可后，进入饮食影响检查

进入前的短文案：`This keeps the draft for the next step; it does not activate it. Next, we’ll check your current meals.`
确认绑定具体草稿版本，旧版本按钮失效并显示 `Replaced by a newer draft`。
Nutrition 只接收会员认可的训练版本和当前饮食，先检查，不默默改食谱。

- 无需调整：简短告知 `Your meals can stay the same.`，进入最终确认。
- 需要讨论：解释具体影响或不确定性，用户此时再做决定。
  - 保留认可的训练：查看具体饮食调整建议，和 Nutrition 多轮讨论。
  - 保留原饮食：把明确约束带回 Coach，修改训练，再由会员认可，重新检查适配。
  - 两边适当调整：专家可以展示一个具体推荐方案，说明训练和饮食各改什么；不能只给抽象的“全部改”按钮。

角色切换只在用户进入下一专业阶段时出现一次。后台验证无需表现为角色反复切换。

### D. 最终确认与启用

最终摘要显示训练变化、饮食是否变化、必要老板审核状态。`Confirm update` 仅在完整校验与必要审核通过后可用。
在系统要求精确配套的情况下，一次原子启用匹配的训练和饮食记录。训练认可只是阶段决定，不能提前启用训练造成版本不匹配。
用户要求“先立即用训练、以后再看饮食”时，必须解释是否支持，不能假装训练已经生效。
认可之后任何实质内容、资料、权限或依赖版本改变，都需重新验证；影响用户已认可内容时重新确认。

## 4. 时间线和输入框

- 输入框固定在视口底部；最新实际消息、阶段结果或待决策卡位于它上方。
- 使用事件发生顺序，不能通过分别遍历消息和任务列表拼接时间线。
- 任务进度在对应阶段卡上更新；完成阶段追加简洁结果，禁止每轮轮询复制一张新卡。
- 旧阶段卡保留历史位置，禁用失效操作并可跳到最新版本；旧 In use 任务不持续占据聊天底部。
- 当前需要用户决定时，卡内同时有必要摘要和明确下一步，用户无需向上找依据。
- 用户在底部时跟随新结果；用户翻阅历史时不抢滚动，显示 `New updates` 返回最新。
- 返回对话恢复位置与草稿；若产生新结果，给可见的新消息提示。
- 刷新和重连恢复同一阶段、卡片与未提交文字，不重新执行操作。

## 5. 所有草稿入口的统一契约

TrainingCandidate、NutritionCandidate、TrainingMealReview、Activity、Updates、老板审批卡、通用 Review 按钮，都必须明确目标类型、记录ID、版本、阶段、来源对话。

- 训练草稿直达该训练版本；饮食草稿直达该食谱；配套确认直达那一组。
- 优先使用独立详情视图/抽屉，避免只靠长页面滚动定位。
- 目标不存在或被替换时明确提示，并给最新版本入口，不退回总页假装成功。
- 刷新、返回和直接访问深链接保持定位；后台重新验证对象所有权。
- 草稿详情明确标为 Draft，当前有效计划明确标为 In use，不能混在一起让用户猜。

## 6. 跨角色和跨权限场景矩阵

| 场景 | 当前接待/第一步 | 进入下一步的条件 | 用户下一步决定 | 生效边界 |
|---|---|---|---|---|
| 查看训练和饮食 | 当前角色读取 | 无须交接 | 可选择深入咨询 | 无写入 |
| 修改训练 | Coach 澄清并出训练草稿 | 会员认可具体训练版本 | Nutrition 检查后按具体结果取舍 | 配套检查、必要审核和最终确认 |
| 首次同时建训练和饮食 | 前台完成资料，Coach 出训练 | 资料资格通过、会员认可训练 | Nutrition 展示饮食草稿 | 完整方案最终确认 |
| 修改饮食 | Nutrition 澄清并出饮食草稿 | 会员认可饮食方向 | 若影响训练，说明影响后再交 Coach | 当前训练不默默改变 |
| 替换一道菜/食物 | Nutrition 定位确切餐次和食物 | 用户选定替换建议 | 确认替换 | 不扩大成整套重做，保留过敏等校验 |
| 训练周期复盘 | Coach 展示已确认反馈和下一周期建议 | 认可下一周期训练草稿 | 必要时检查饮食影响 | 记录反馈不等于批准新计划 |
| 新伤情或资料变化 | 暂停受影响修改，前台收集资料 | 会员确认资料、必要老板审核 | 返回原目标，说明需重算部分 | 不沿用失效草稿的确认 |
| 会员入会审核 | 前台收集，会员确认提交 | 老板 Updates 收到具体申请 | 老板审批；会员收到结果 | 提交、批准、服务可用分开显示 |
| 老板要求修改计划草稿 | 老板说明具体原因 | 对应专家修订 | 会员重看受影响内容，必要时重审 | 老板批准不替代会员启用 |
| 预算/额度阻塞 | 当前任务说明等待事项 | 老板在 Updates 调整规则 | 会员收到恢复或仍阻塞原因 | 不替会员批准后续计划阶段 |
| 老板修改额度/成员组 | Technical Manager 解析对象、显示差异 | 明确对象和影响后确认 | 保存回执或准确详情入口 | 同名需澄清；不得跳过权限 |
| Agent 评估与发布 | Technical Manager 展示证据 | 人工评审与发布审批分别满足 | 执行发布并显示结果 | 通过评估、批准、部署不是同一状态 |
| 故障与未知费用 | Technical Manager 给出事实与可执行选项 | 老板选择恢复、知悉归档或核实 | 明确回执 | 归档不等于费用结算或故障恢复 |

## 7. 多轮、多版本和异常边界

- 同一目标内连续修改是同一流程的草稿修订；保留版本链和会员反馈，不丢原目标。
- 用户打断去问无关问题时可以回答，但不自动取消原草稿或推进下一阶段；提供返回入口。
- 另开会话修改同一计划时提示现有任务的具体入口，不允许两个结果互相覆盖。
- 连点、双标签页、刷新重复提交：同一阶段决定幂等；旧版本确认返回最新结果或明确冲突。
- 生成期间取消：停止未执行后续步骤；迟到的模型结果不得成为可启用草稿。
- 老板退回、资料更新、权限变更或计划被别处替换：使相关阶段认可失效并解释原因。
- 多个老板审核同一事项：第一个有效决定生效，其他界面同步，不能重复执行。
- 系统不知道适配结果时显示不确定性和可行下一步，不把格式校验通过冒充医学适配结论。

## 8. 实现分层与优先顺序

P0：持久化阶段与版本绑定。区分训练讨论、等待训练认可、饮食检查、饮食讨论、等待老板、等待最终启用、完成、取消。阶段转换在服务端校验，不能仅靠前端按钮隐藏。

P0：训练修改真正切换当前接待角色；同一目标的后续意见传入当前草稿修订，不触发“另有更新，请先取消”的错误分支。

P0：Coach 完成后停止自动派发 Nutrition。只有认可当前训练草稿的动作才能排入下一步。阶段恢复也遵守此门槛。

P0：统一事件时间线与精准详情导航，删除底部重复的全量任务展示方式。

P1：把首次组合建计划、饮食反向影响训练、周期复盘、老板退回纳入同一分阶段机制。保留替换单项等更短的流程，不为了统一强加无用步骤。

P1：统一审批、阻塞、异常和恢复提示，所有角色的权限由后端控制。

## 9. 必须通过的验收

1. 从 Nutrition 对话提出训练修改后，接待角色为 Coach；仅查看训练不会强制切换。
2. 训练草稿生成后，会员未认可时 Nutrition 调用次数为零。
3. 连续修改训练三轮，只有最新草稿可认可；不会出现阻止同一目标继续讨论的任务冲突。
4. 认可后只启动一次饮食检查；刷新、重连、连点不能重复派发。
5. 饮食不变、改饮食、保饮食改训练、两边调整均有清楚的当前阶段与最终确认。
6. 阶段认可前后 CurrentPlans 都不变；最终启用一次性更新匹配版本。
7. 所有 Review 入口都打开准确记录，包含旧链接、替换版本和不可用记录场景。
8. 最新结果在时间线末端；旧 In use 卡不压在新结果下面；阅读历史时不强制拉回底部。
9. 老板审批与会员确认分开验证；退回后的新版本不能沿用旧确认。
10. 取消、额度恢复、并发修改、过期、跨账号访问均不绕过阶段或权限。
11. 浏览器验收覆盖桌面与窄屏，验证对话内修改和来回详情页，而不只检查构建。
